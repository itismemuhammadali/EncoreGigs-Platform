- **Privacy Settings (Show Phone Number, Activity Status, Search Engine Indexing)**:
  - Client Feedback / Inquiry (08:00 - 08:30):
    1. **"Show Phone Number"**: Asked what this setting does.
       - Explanation: When enabled and if the musician has a phone number saved on their account, organizers who view their profile (e.g. after they apply to a gig) can see their phone number directly in a dedicated "Contact Information" section to reach them quickly. If disabled (or no number is saved), the phone number remains strictly private and hidden.
    2. **"Activity Status"**: Asked what this setting does.
       - Explanation: When enabled, displays an "Active now" neon status badge with an indicator light on the musician's profile, signaling to organizers that the musician is active on the platform. If disabled, activity is hidden.
    3. **Live Firestore Persistence**: All toggles on the Privacy Settings screen (`profileVisibility`, `showEmail`, `showPhone`, `showLocation`, `activityStatus`, `searchEngineIndexing`, `profileVisibilityOption`) were previously local state. They now dynamically load from and persist to Firestore (`musicians` and `users` collections) instantly on toggle.
    4. **"Search Engine Indexing"**: Asked what this setting does.
       - Explanation & Talent Discovery: Controls whether the musician's profile is indexed in the Organizer's **"Find Talent" / Musician Search** screen. When enabled, organizers searching for talent find musicians ranked by rating, review count, and featured artist status. If a musician disables Search Engine Indexing (or Profile Visibility), their profile is omitted from public talent search results.

- **Data & Privacy: Download User Data (Complete ZIP Archive vs Raw JSON)**:
  - Client Feedback / Issue (08:30 - 08:50): When tapping "Request Data Export" under Settings -> Data & Privacy, the app popped up an alert displaying raw monospace JSON code on screen instead of providing a downloadable user archive with all media/portfolio files.
  - Fix: Fixed.
    1. Built a backend streaming endpoint (`GET /auth/download-data/{uid}`) that compiles a complete in-memory ZIP package.
    2. The ZIP archive contains:
       - `account_summary.html`: A styled, human-readable account report complete with profile summary, gigs, applications, bookings, transactions, and reviews.
       - Full JSON data files (`profile.json`, `applications.json`, `bookings.json`, `transactions.json`, `chats_and_messages.json`, `reviews.json`, `notifications.json`).
       - `portfolio/` folder: Directly downloads and includes the musician's portfolio media files (audio tracks, images, videos, avatar) and generates a manifest file.
    3. Updated both Musician and Organizer `data_privacy_screen.dart` to trigger the live download to the user's device Downloads folder and show a clear, reassuring confirmation dialog detailing what was packaged.

- **My Contracts Screen**:
  - Client Feedback / Observation (~08:50 - 09:05): Client navigated into "My Contracts". The screen displayed "No contracts found".
  - Explanation: This is completely normal and intended behavior for this test account. The "My Contracts" screen displays active gig contracts once an organizer has accepted an application, hired the musician, and established a formal contract. For accounts that have not yet had contracts generated or signed, the screen gracefully shows an empty state illustration with "No contracts found".

- **Admin & Support Chat: File & Media Attachment Uploads (`live_chat_screen.dart` & `support_chat_service.dart`)**:
  - Client Feedback / Issue (~09:05 - 09:30): In Admin & Support Live Chat, client sent messages ("hello") and then tapped the attachment icon / file picker to attach and send a document/file, but nothing happened.
  - Root Cause & Fix:
    1. **Older Build Root Cause**: In the older test build the client was running, the attachment icon (`assets/attach_files_icon.svg`) and photo icon (`assets/image_icon.svg`) were visual placeholders with empty callbacks (`onTap: () {}`) and greyed-out styling.
    2. **Verified & Enhanced Implementation**: In the current codebase, both file picking (`FilePicker.platform.pickFiles()`) and photo picking (`ImagePicker` via Camera or Gallery) are fully hooked up to `SupportChatService.sendAttachmentMessage()`, which uploads files to Firebase Storage (`chat_attachments/support/$userId/`) and renders rich preview bubbles with download/open links.
    3. **Android 13+ (API 33+) Media Permissions**: On modern Android devices, legacy `READ_EXTERNAL_STORAGE` is ignored. We added `READ_MEDIA_IMAGES`, `READ_MEDIA_VIDEO`, and `READ_MEDIA_AUDIO` to `AndroidManifest.xml` across both Musician and Organizer applications so file and photo pickers cannot be blocked by system permission restrictions.

  - Client Feedback (~11:00 - 11:30): Client navigated to "Dispute Management" and tapped "Create New Dispute", but could not proceed or submit a dispute.
  - Explanation: In OnlyGigz, a dispute is a formal contract/escrow dispute tied directly to a specific booked gig between a musician and an organizer (governed by Section 14 and Section 27 of the Terms of Service). Because the test account has zero active gigs/bookings, the "Choose a gig with issue" dropdown properly displayed "No active gigs found" and disabled submission. A dispute cannot be initiated without an associated gig transaction. When an account has booked gigs, the dropdown populates all active gigs for the user to select, choose a dispute category (Payment, Cancellation, Performance Quality, Agreement Breach, etc.), provide a description, and upload up to 5 evidence documents.

    4. "Open in Browser" button included on every policy screen.

- **App Version Numbering vs APK File Names (`settings_screen.dart`)**:
  - Client Feedback (~12:15 - End of Video): Client questioned why the in-app version displayed in Settings (e.g. "Version 1.0.0") does not match the test APK build version / filename.
  - Industry Standard Explanation:
    1. **Store Release Versioning**: In mobile application development for Apple App Store and Google Play Console, the in-app version number (`1.0.0`) represents the official base release version target submitted for store review and publication. It is only incremented when an official new production release is staged for public release.
    2. **Test Artifact Naming**: During active development and QA cycles, APK filenames (e.g. `onlygigz-musician-v1.0.2-debug.apk` or timestamped test builds) are labeled by the development team specifically for artifact identification and distribution. This ensures clients and QA testers do not accidentally install or mix up older and newer test files on their devices.
    3. **Production Alignment**: When the final release bundle is compiled for official store launch, the in-app version and store release version will be aligned to the client's chosen release version.
